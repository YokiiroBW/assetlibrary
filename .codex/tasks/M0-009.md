## 目标

把 M0-001 至 M0-008 的可执行证据收敛成一套可审查、可自动执行、可回滚的架构冻结结果：明确哪些能力已经成立，哪些剩余门禁阻断 V0.1、阻断后续平台/发行，或应被拒绝；冻结语言与框架预算、模块依赖、共享契约/迁移所有权和 CI 分层。只有本任务最终通过，主协调线程才可批准 V0.1 大规模实现。

本任务是裁决与门禁实现任务，不是补做所有平台 Spike，也不是产品功能开发任务。

## 输入状态与真实性约束

任务注册表显式接纳以下 `partial` 依赖作为待裁决输入，并保持其原状态：

| 任务 | 已有证据 | 仍未证明的关键项 |
|---|---|---|
| M0-002 | HKCU 注册/清理、Shell bind、隔离 view window、微软 Shell32 真实 Explorer 控制组 | 自定义 DLL 的受支持发现/部署路径、真实 Explorer custom view、故障恢复、20 次循环与 8 小时 soak |
| M0-004 | 单核心 Windows/Linux 冷发布与 manifest、Windows 普通进程生命周期 | Windows Service 管理员周期、真实 Docker/Compose 与容器边界 |
| M0-006 | Linux 40 项与 Windows 小型 NTFS no-replace/强哈希/进程崩溃恢复证据 | 1/20/100 GiB、突然断电/目录项持久性、Linux 非协作 namespace mutation 策略 |
| M0-008 | Windows Job Object 与 Restricted Token 降权/资源限制 | Windows 文件和网络 deny-by-default、Linux hard confinement、RPC cancel acknowledgement |

不得因为 M0-009 被激活而把上述任务改成 `completed`。不得把测试跳过、控制组结果、API 返回成功、普通进程测试或 Restricted Token 降权写成未取得的生产保证。

对每个残余门禁必须选择且只选择一种结论，并写明证据、影响、责任任务和解除条件：

1. `blocking_v0_1_start`：不解决就不能开始相应 V0.1 实现；
2. `deferred_fail_closed`：不阻断 V0.1 开发，但相关入口、发行或能力默认不可达，并有自动门禁防止提前启用；
3. `blocking_release_or_later_milestone`：允许核心实现，阻断指定平台、发行包或后续里程碑验收；
4. `rejected`：候选方案被否决，记录替代方向和不得继续使用的边界。

`deferred` 不能只写文字承诺，必须对应明确的范围排除、默认关闭策略或可执行检查。下列仅是待验证的裁决假设，不是预先批准的结论：Explorer 可依据 ADR-0006 延后至 V0.5；可选 Provider 可在硬隔离成立前保持不可用；发行验证可与核心实现分层；涉及 V0.1 真实写入安全的缺口可能仍是 V0.1 阻断项。

- 逐项核对 M0-001 至 M0-008 的分支提交、diff、测试计数、平台跳过、风险和 blockers。

- 若仍有 `blocking_v0_1_start`，本任务必须以 `partial` 或 `blocked` 交接，不得宣布 M0-009 通过。

### 2. 技术栈与所有权冻结

- 根据 Spike 证据冻结各平台主语言、主框架和受支持版本范围；未获证据的选择必须保持候选或拒绝，不能伪装为已验证。
- 更新 ADR-0012/ADR-0013，或新增最小必要 ADR，记录选择、证据、替代方案、升级/退出策略和重大依赖约束。
- 冻结模块目录、依赖方向、跨模块公开交互方式、数据库表/迁移单一所有者、AssetLink/Provider 契约所有者和生成 SDK 所有者。
- 明确 PostgreSQL 即可满足当前核心需求时，不得引入 Redis、第二数据库、独立搜索或消息集群。

### 3. 可执行架构门禁

- 把 `tests/architecture/architecture-rules.json` 和政策文本转成真实的阻断检查，而不只是“文件存在”检查。
- 至少覆盖：Domain 反向依赖、跨模块 Infrastructure/内部实体引用、循环依赖、客户端/Provider 直连 PostgreSQL、Shell 重型/网络/数据库依赖、语言预算、无边界 `common/shared/utils/helpers`、共享契约消费者一致性。
- 每条新规则必须有一个应通过夹具和一个应失败夹具，证明检查不是恒真。
- 空目录或尚未创建的平台不得被误报为“已验证”；应明确输出 not-applicable 或尚未启用的层级。
- 不得为做门禁而引入第二套同职责构建系统或大型依赖。

### 4. CI 分层与 V0.1 启动合同

- 冻结至少三层：每次合并的快速阻断门禁、平台/依赖环境门禁、定时或发布级故障/性能/soak 门禁。
- 每层列出实际命令、运行器、超时、缓存、产物、失败策略和哪些跳过可接受；平台缺失不能被当作通过。
- 覆盖格式化、静态/类型检查、架构、契约与生成 SDK、迁移、单元、集成、安全、故障恢复、性能、依赖漏洞、许可证和敏感日志扫描；若某工具尚未选定，须记录冻结前置条件而非发明假命令。
- 定义 V0.1 可创建的任务图、模块所有权、共享契约单一 owner、建议合并顺序和禁止并行修改区域；由主协调线程在 M0-009 合并后更新注册表和项目状态。

- 新语言/框架：默认不新增；若确需新增，必须先批准 ADR 并记录完整依赖评估。
- 共享契约/迁移：本任务默认不改；只冻结 owner、兼容策略和门禁。

## 安全、兼容与性能约束

- 所有会写文件或制造故障的验证只可使用 `.runtime/sandbox-storage/` 或系统临时目录，并先验证边界；不得碰真实资产。
- Windows 管理员、HKLM/SCM、AppContainer、Docker、Linux namespace/cgroup 或大文件测试仍须各自满足审批和专用环境边界；本任务不能扩大授权。
- Explorer 相关规则必须保持进程内最小化和有界响应；未完成 M0-002 门禁前不得创建生产 Shell 实现。
- Provider 硬隔离未成立时，默认不得启用不可信 Provider；Restricted Token/Job Object 不能单独表述为完整沙箱。
- 50 万资产、100 GiB、故障和 soak 的 CI 分层必须记录真实资源预算；不得用空跑、稀疏文件或跳过冒充通过。
- 无 AI、无在线 Provider、无 WebDAV/MCP 时，核心能力仍须可用。
