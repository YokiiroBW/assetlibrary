## 冻结的 schema 与角色所有权

生产 schema 名使用小写 snake_case，业务模块名仍以架构文档中的 PascalCase 为权威：

| 模块 | schema | owner role | runtime role |
|---|---|---|---|
| GatewayAuth | `gateway_auth` | `assetlibrary_gateway_auth_owner` | `assetlibrary_gateway_auth_runtime` |
| LibraryStorage | `library_storage` | `assetlibrary_library_storage_owner` | `assetlibrary_library_storage_runtime` |
| AssetIdentity | `asset_identity` | `assetlibrary_asset_identity_owner` | `assetlibrary_asset_identity_runtime` |
| MetadataSidecar | `metadata_sidecar` | `assetlibrary_metadata_sidecar_owner` | `assetlibrary_metadata_sidecar_runtime` |
| ScanReconciliation | `scan_reconciliation` | `assetlibrary_scan_reconciliation_owner` | `assetlibrary_scan_reconciliation_runtime` |
| TransferSync | `transfer_sync` | `assetlibrary_transfer_sync_owner` | `assetlibrary_transfer_sync_runtime` |
| OperationTrash | `operation_trash` | `assetlibrary_operation_trash_owner` | `assetlibrary_operation_trash_runtime` |
| SearchDedup | `search_dedup` | `assetlibrary_search_dedup_owner` | `assetlibrary_search_dedup_runtime` |
| PreviewProvider | `preview_provider` | `assetlibrary_preview_provider_owner` | `assetlibrary_preview_provider_runtime` |
| TaskHealth | `task_health` | `assetlibrary_task_health_owner` | `assetlibrary_task_health_runtime` |
| BackupUpdate | `backup_update` | `assetlibrary_backup_update_owner` | `assetlibrary_backup_update_runtime` |

`migration` schema 与执行 ledger 只归 `assetlibrary_migration_owner`。`assetlibrary_migration_executor`、只读的 `assetlibrary_database_backup`、`assetlibrary_database_auditor` 及上述角色均为 `NOLOGIN`、`NOSUPERUSER`、`NOCREATEDB`、`NOCREATEROLE`、`NOREPLICATION`、`NOBYPASSRLS` 组角色；部署登录账号和凭证由发行/密钥管理任务另行配置，不写入仓库。runtime 只获得本 schema 的 `USAGE` 和由对应 owner 创建对象的默认 DML 权限，不继承 owner，不得跨 schema 写。backup role 只获得所有模块表/序列的读取权，专用于迁移前 `pg_dump`；跨模块业务读取仍必须由后续 owning module 以显式只读投影逐项授权。

所有固定角色的角色属性仍为 `NOINHERIT`。唯一显式成员关系例外是无登录的 `assetlibrary_migration_owner` 以 `INHERIT TRUE, SET TRUE, ADMIN FALSE` 获得 11 个无登录 module owner，用于一次性建立其 default privileges；部署 login 到 executor/migration owner 的链保持 `INHERIT FALSE`，runtime 永不继承或切换 owner。预配工具发现固定角色存在清单外的出向成员关系或错误成员选项时必须失败。

本任务的“权限投影”仅为 `migration.module_privilege_projection`：从系统目录投影期望与实际 schema owner/runtime 权限，供迁移审计角色只读查询。它不是用户/资源库业务权限模型；该模型及其查询合同由 V01-004/V01-006 的指定 owner 创建，避免本任务提前复制权限业务逻辑。

## 迁移与恢复合同

- manifest 是生产迁移顺序、文件名、模块 owner、SHA-256 和 PostgreSQL major 的唯一来源；目录中多余、缺失、重号、乱序、哈希漂移或非 UTF-8/LF SQL 均阻断。
- 迁移为 forward-only。已记账文件禁止修改；修正必须获得新序号。每个迁移在单事务中获取固定 advisory lock、校验完整 ledger 前缀、以 manifest 指定 owner 执行，再记录版本/名称/module/checksum/server version/备份标识。
- 默认入口只做静态校验。`apply` 必须同时提供目标连接、`--confirm-database` 精确匹配和备份目录；密码仅通过 libpq 支持的环境/密钥机制提供，禁止命令行密码和日志回显。
- 有 pending migration 时，任何 DDL 前先用同 major `pg_dump --format=custom` 生成临时 archive，用 `pg_restore --list` 验证，计算 SHA-256 并原子发布 archive + metadata；备份失败或版本不符时迁移不开始。
- `restore` 校验 metadata/archive hash，只恢复到显式确认且不存在用户对象/ledger 的空数据库；使用 `pg_restore --single-transaction --exit-on-error`，不执行 drop/create，不覆盖原库。
- 角色是 cluster-global 前置条件，不能由数据库 archive 完整携带。固定 NOLOGIN 角色预配置 SQL 单独、幂等、可审计；跨集群恢复先预配角色再恢复。产品用户/库权限是数据库业务数据，后续按 ADR-0008 纳入软件备份；数据库密码不写入备份元数据。

## 架构、复用与安全说明

- 复用 M0-005 证实的 PostgreSQL 16.15、advisory lock、事务 DDL、checksum 与真实隔离集群测试；不复制其 Spike 业务表。
- 复用 Python 3.12+ 标准库做 migration tooling/test orchestration，SQL 仍是数据库语言；不新增生产运行时或第三方 Python 包。
- 角色边界通过 PostgreSQL 原生 owner、`SET ROLE`、schema ACL 与 default privileges 实现。创建具体对象的未来迁移必须使用对应 owner，跨模块投影必须由源模块 owner 显式授权。
- 工具必须有有限超时、确定性错误、无敏感连接日志、原子备份 metadata，并在失败时优先保留原数据库和备份证据。
- 50 万资产查询/索引没有在本任务改变，因此不重复 M0-005 的 500k profile；本任务只验证迁移元数据和 catalog 查询为固定 schema/role 数量的有界操作。
- Windows 本地证据只使用 `.runtime/sandbox-storage/V01-003/` 内的 EDB PostgreSQL 16.15 zip binary，监听 loopback 随机端口，测试结束停止并清理数据；不注册服务、不改 PATH。CI 使用隔离 PostgreSQL 16.15 服务。
