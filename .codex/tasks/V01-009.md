## 证据真实性与状态语义

- `integration audit passed`：只表示清单完整、引用存在、状态与机器事实一致、所有缺口均被阻断；允许在 release decision 为 `blocked` 时通过。
- `release ready`：只有全部必需 Alpha 能力为 `passed`、全部必需 task/evidence 为可接受完成状态、且所有要求的 release target 实际返回允许时才成立。
- `partial`、`blocked_missing_environment`、`skipped`、静态文件存在和脚本文本匹配均不得折算为 `passed`。
- `V01-008` 的受控 partial 例外只允许 V01-009读取并报告；不能修改上游状态。
- 当前实现预期 release decision 为 `blocked`。若当前仓库意外得到 `ready`，验证器必须失败并要求协调线程独立核对真实证据与 gate 解除提交。

## 必须实现

### Alpha readiness 政策

- 新增单一机器源 `eng/v0.1-alpha-readiness.json`，使用版本化合同 `v01-009/1`。
- 固定 V0.1 必需能力全集，至少覆盖：构建/依赖、AssetLink/SDK、PostgreSQL 迁移与恢复、Library/Asset/初扫只读核心、权限与分页只读网关、TaskHealth/outbox、Transfer/Operation、生产身份认证、生产数据库/迁移组合、host 业务 API、TLS/secret、标签元数据、精确查重、软件备份/恢复、50 万资产/大文件与故障证据、Windows/Linux/Docker 发行证据。
- 每项记录稳定 ID、当前状态、证据来源、release 阻断语义、唯一 owner 与后续任务；缺实现或缺环境必须显式写出，禁止空 blocker。
- 固定受控任务输入及其 registry/handoff 预期状态；V01-008 必须保持 `partial` 与 adjudication-only。
- 发布判定只由验证器从能力与 gate 事实计算，JSON 中的声明不能覆盖计算结果。

### 审计与发布入口

- 新增 `scripts/validate_v0_1_alpha.py`，仅使用 Python 标准库，默认进行无写入审计并返回 0；输出稳定、低敏的 `ALPHA_INTEGRATION_AUDIT_OK decision=blocked|ready`。
- 验证 JSON schema 形状、唯一/完整能力 ID、允许状态、证据路径 containment/存在性、任务 registry/result 状态、受控 partial 输入、V01-008 host policy 的 `business_api_ready=false` 与 `production_file_writes_enabled=false`，以及必需 release targets 的实际机器判定。
- 复用 `tests/architecture/check_release_gates.py` 的可执行判定，不复制另一套 gate 允许算法。子进程必须使用当前 Python、绝对脚本路径、有界超时和明确退出码。
- `--require-ready` 在任一能力或 release target 未通过时返回稳定退出码 3，并按稳定 ID 输出阻断项；审计错误返回不同的非零退出码，不能与“证据有效但未 ready”混淆。
- 可选 `--output` 只允许写入当前 worktree `.runtime/sandbox-storage/V01-009/**` 的带 owner marker 真后代，默认完全只读；不得接受 UNC、设备、reparse、仓库根、用户目录或真实资产路径。
- 报告不得包含绝对用户路径、主机名、账号、连接串、token、凭据或资产数据。

### CI 与文档

- `scripts/verify_repository.py` 与 `fast-merge` 只运行默认审计，确保清单和阻断事实不可漂移；它们不得要求当前发布 ready。
- `scheduled-release` 的人工 release-readiness job 必须运行 `--require-ready`，在当前状态下按设计失败；不得 `continue-on-error`、条件性吞错或把退出码 3 当成功。
- `tests/architecture/ci-tiers.json` 与实际 workflow 的命令必须同步。
- 新增 `docs/releases/V0.1_ALPHA_READINESS.md`，清楚区分“已验证组件”“尚未集成/实现”“外部环境门禁”和“何时才可称为 release candidate”，并给出后续任务顺序。

## 架构、所有权与复用

- 所属模块为仓库/发布集成工具，不进入产品运行时，不拥有任何业务数据或模块状态。
- 复用 `m0-gates.json` + `check_release_gates.py` 作为 release target 的唯一允许判定；复用 task registry/result、V01-008 host policy 与现有 CI tier，不创建平行事实源。
- 只读取公开 handoff/机器政策，不引用其他模块 Infrastructure、内部实体或数据库表。
- 不复制权限、传输、文件状态机、迁移或 host 逻辑；只对其现有证据作编排与一致性校验。
- 不新增语言、框架、运行时、第三方包或服务。

## 自动测试与负向验收

- 正常审计：当前仓库政策有效且计算结果严格为 `blocked`。
- 发布入口：`--require-ready` 返回 3，输出至少包含当前未实现能力与 `v0.1-release` 的开放 gate。
- 变异测试：删除必需能力、伪造 `passed`、把 V01-008 改完成、接受 skipped/partial、篡改 task/result 路径、越界 evidence path、声明 ready、移除 owner/follow-up/blocker、无效 gate ledger/超时/异常均失败关闭。
- output 路径：默认无写；合法任务沙箱生成脱敏、确定性 JSON；越界、根本身、reparse、UNC/设备路径全部拒绝且不留下半文件。
- CI 合同：fast-merge 运行 audit，人工 scheduled release 运行 require-ready，无 `continue-on-error`。
- 运行 repository、architecture、release、database、.NET、SDK/AssetLink、Web 与 `v0.1-start`；`v0.1-release`/`--require-ready` 的退出 3 是经断言的预期阻断，不可计作通过用例。

## 性能、安全与文件影响

- 审计只读取小型 JSON/Markdown/政策文件并启动少量有界 gate 子进程；复杂度与资产数量无关，不扫描资产内容。
- 输出采用原子替换、owner marker、canonical containment 和 no-follow/reparse 拒绝；不读取或写入真实资产、NAS、数据库或系统状态。
- 任何异常、缺文件、状态漂移或未知枚举均判为 audit error；任何未通过能力/gate 均判为 release blocked。
