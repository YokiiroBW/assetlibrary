## Required outcomes

1. Verify the current supported PostgreSQL candidate from primary official
   documentation. Record the exact server/client version tested, support
   status, license, package source and URLs; do not equate the available client
   version with the chosen server version without evidence.
2. Bootstrap a disposable local cluster whose data, socket, logs and temp files
   remain under the isolated runtime area or system temp. Use trust only on its
   private local socket for this ephemeral test cluster; never expose it on a
   network interface. Stop it and remove generated data after evidence capture.
3. Deliver a candidate migration layout under `database/**` with explicit
   module-owned schemas/tables, a migration ledger/checksum, serialized
   migration ownership, transactional failure behavior and forward-only
   production policy. Reapply must be idempotent or fail deterministically;
   a deliberately failing migration must leave no partial objects.
4. Model only the minimum needed to validate the decision: physical-library
   and asset identity/search projection, durable tasks, leases/heartbeats, and
   an outbox. Store library ID plus relative path and hashes; do not make an
   absolute path or database row the physical-file authority. Do not attempt the
   complete V0.1 domain model.
5. Prove competing workers claim tasks exactly once per active lease using
   PostgreSQL locking such as `FOR UPDATE SKIP LOCKED`; prove heartbeat owner
   checks, expired-lease reclaim, bounded retry/attempt state, cancellation and
   idempotency-key behavior. A crashed worker must not permanently strand work.
6. Prove a state change and outbox event commit atomically. Publisher claims may
   be at-least-once, but duplicate delivery must have an explicit idempotency
   identity and a retryable unpublished state; do not claim exactly-once
   delivery.
7. Load a deterministic 500,000-asset metadata dataset and test permission-
   bounded keyset pagination, filename/path filters, PostgreSQL full-text search
   and trigram search. Capture `EXPLAIN (ANALYZE, BUFFERS)` plans, index usage,
   dataset size and repeated-query latency distribution. Treat measurements as
   host-specific evidence, not unconditional production thresholds.
8. Exercise restart persistence, concurrent claims, duplicate request retry,
   lease expiry, failed migration and outbox retry. All fixtures use synthetic
   IDs/paths; no real NAS path, asset, credential or private metadata may appear.
9. Document whether PostgreSQL alone is sufficient for this scope, the query/
   migration ownership rules to freeze in M0-009, and any evidence-based trigger
   that would justify a future cache/search component through ADR.

## Interfaces and compatibility

- PostgreSQL SQL is the database language. Python may only orchestrate tests,
  synthetic data and evidence; no Python production data layer is introduced.
- Each schema/table has one module owner. Cross-module writes are forbidden;
  read sharing must be a named projection, event or approved query contract.
- IDs, states, hashes and timestamps are explicit. Timestamps are UTC-aware;
  asset sizes are 64-bit; paths are relative and normalized outside SQL by the
  future core.
- Task/outbox operations are transactionally bounded, cancellation-aware where
  applicable, and safe under retry. SQL errors must be visible and logs must not
  contain credentials or real user paths.
- No candidate SQL becomes a frozen production contract until M0-009 accepts it.
