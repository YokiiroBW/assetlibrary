# 22. 编码与架构开发原则

本章是强制开发基线，不是建议性风格说明。实现“能够运行”但违反模块边界、重复业务逻辑、引入无批准技术栈或无法自动验证的代码，不得合并。

## 22.1 架构风格

项目采用：

```text
领域模块化单体核心
+ 端口与适配器（Ports and Adapters）
+ 隔离 Worker / Provider 进程
```

首期不把个人 NAS 系统拆成大量微服务。模块边界必须清晰，但默认在同一服务端核心中部署；只有需要崩溃隔离、资源限制、平台专用依赖或独立扩缩容的重型能力才进入 Worker。未来拆分必须基于真实负载与 ADR，而不是为了架构图好看。

## 22.2 强制依赖方向

```text
UI / AssetLink / WebDAV / Developer API / MCP / CLI
                         ↓
                     Application
                         ↓
                       Domain

Infrastructure / Provider Adapter
        └── 实现 Application 或 Domain 定义的端口
```

- `Domain` 不得依赖 UI、HTTP、数据库、文件系统、操作系统、缓存、消息总线或具体 Provider。
- `Application` 编排用例、事务和权限，但不得直接绑定具体 PostgreSQL、SMB、NTFS 或 Android API。
- `Infrastructure` 实现存储、文件系统、网络、缓存、时钟、哈希和消息端口。
- UI 与协议入口只做输入输出适配、鉴权上下文和展示映射，不重新实现业务规则。
- 跨模块调用只能通过公开命令、查询、端口、版本化契约或领域事件；禁止引用其他模块内部类与内部表。
- 禁止循环依赖。为了“临时方便”增加反向引用也视为架构缺陷。

## 22.3 模块数据所有权

每个模块对自己的状态、表、写模型和迁移负责。共享一个 PostgreSQL 实例不等于所有模块可以任意读写所有表。

例如：

```text
Transfer 模块拥有 transfer_sessions
Search 模块不得直接 UPDATE transfer_sessions
需要改变传输状态 → 调用 Transfer 的公开 Application 接口
```

跨模块高性能读取应使用明确的只读投影、事件构建的索引或批准的查询契约，不能借性能之名绕开写入边界。数据库迁移、权限语义、统一错误码和共享契约必须有单一所有者。

## 22.4 业务逻辑只实现一次

下列规则必须由服务端领域/应用层统一实现：

- 资源库权限与访问通道判断；
- 路径规范化与资源库边界检查；
- 稳定资产身份、复制/移动判断和强哈希；
- 文件稳定性检测与临时接收；
- 传输状态机、同步基线与冲突分类；
- 复制、移动、改名、替换、保护与垃圾桶；
- Sidecar、复合资产和操作锁；
- 精确查重、审计、通知和 Provider 调度。

Web、Windows、Android、Explorer、WebDAV、Developer API 和 MCP 只能调用同一个用例。客户端可做体验性预校验，但服务端必须重新校验并作为最终权威。

## 22.5 复用边界

必须共享：

- AssetLink、事件、操作计划和统一错误码契约；
- 由契约生成的 .NET、TypeScript、Kotlin SDK；
- 权限、状态机、哈希与物理操作语义；
- Windows 独立客户端与 Explorer 可安全复用的视图模型/组件；
- 设计令牌、图标语义和状态词典。

不强行共享：

- Android、Web 与 WinUI 的原生控件；
- 平台导航、窗口生命周期、触摸和键鼠交互；
- 为追求表面复用而引入的跨平台 UI 大一统框架。

复用业务语义与契约，不把不同平台的 UI 硬塞进同一套运行时。

## 22.6 语言与框架预算

每个平台只允许一个主语言和一个主 UI/服务框架。默认候选预算如下，最终由 M0 Spike 与 ADR 冻结：

| 范围 | 默认候选 | 约束 |
|---|---|---|
| 服务端核心、Worker、Windows 服务端 | C# / .NET | Windows、Linux、Docker 共用同一核心 |
| Windows 独立客户端、AssetHost | C# / WinUI 3（或验证后的等价方案） | 不再引入第二套桌面 UI 框架 |
| Windows Shell | C++ / WinRT / COM | 仅命名空间、菜单、IPC和最小桥接 |
| Web | TypeScript / React | 新业务禁止裸 JavaScript |
| Chromium 扩展 | TypeScript | 复用生成的 TypeScript SDK |
| Android / 平板 | Kotlin / Jetpack Compose | 新业务不混入 Java |
| 数据库 | PostgreSQL SQL | 迁移和经验证的性能查询 |
| 工具与生成脚本 | Python | 仅构建、测试、生成、仓库管理 |

未经批准 ADR，禁止新增另一套服务端、数据库、消息平台、搜索集群、前端框架、桌面框架或主编程语言。依赖引入必须说明维护成本、许可证、安全更新、二进制体积、跨平台和替代方案。

## 22.7 仓库与模块目录

顶层目录按产品入口和边界组织：

```text
apps/           官方客户端与用户入口
services/       核心服务端与 Worker Supervisor
gateways/       WebDAV 等协议网关
integrations/   MCP、AstrBot、Hermes、Codex 等适配
providers/      可隔离的格式/分析 Provider
contracts/      版本化共享契约与 Schema
packages/       真正稳定、可复用的 SDK/设计令牌/测试支持
infra/          Docker、Windows、Linux 与 CI 发行配置
tests/          单元、集成、契约、架构、端到端、性能与故障注入
docs/           需求、架构、ADR 与开发规范
```

服务端模块内部使用以下结构或经 ADR 批准的等价结构：

```text
Modules/<ModuleName>/
├─ Domain/
├─ Application/
├─ Infrastructure/
└─ Contracts/
```

禁止把项目逐渐堆成 `Controllers/Services/Repositories/Utils` 横向大杂烩。禁止创建无明确边界的 `common`、`shared`、`utils`、`helpers` 万能目录。代码被两处使用不等于应立刻进入共享包；只有稳定、职责清楚且有多个真实消费者的内容才能上移。

## 22.8 代码设计原则

- KISS：选择最容易验证、恢复和维护的方案。
- YAGNI：没有真实需求与两个实现前，不预建万能抽象。
- 单一职责：避免 God Service、God Repository、God ViewModel。
- 显式优先：使用明确状态、错误类型、权限、目标路径、事务和取消，不靠布尔组合与魔法字符串表达业务。
- 组合优先于深继承；接口按使用方能力拆分，不建巨型接口。
- 不允许共享可变全局状态；时间、文件系统、网络、随机数等外部依赖应可替换测试。
- 所有 ID、状态、路径和哈希使用明确值对象或类型，不在边界内长期传递裸字符串。
- 注释解释“为什么”和不明显的约束，不逐行复述代码。
- TODO 必须关联任务 ID、责任范围和清理条件；禁止永久无主 TODO。
- 生成代码不得手工修改；契约变化后重新生成并执行消费者测试。

## 22.9 异步、错误与可恢复性

所有 I/O 与长任务必须具备：

- 取消、超时和资源上限；
- 幂等键或清晰的不可重试边界；
- 结构化错误码、用户说明和开发者上下文；
- `request_id`、`task_id`、`plan_id`、`transfer_id` 等关联标识；
- 可恢复检查点与部分成功结果；
- 不吞异常，不使用空 `catch`，不依赖解析错误字符串驱动业务。

文件操作成功必须通过目标可重新读取与强哈希验证，不能只相信系统调用返回成功。

## 22.10 测试分层

每个模块至少具备：

```text
单元测试        领域规则和状态机
集成测试        PostgreSQL、文件系统与进程边界
契约测试        AssetLink、事件、Provider、API消费者
架构测试        依赖方向、模块引用、循环依赖、语言预算
端到端测试      关键用户闭环
故障注入        断网、崩溃、空间不足、部分写入、重复重试
性能回归        50万资产、100GB文件、瀑布流和查询P95
安全测试        权限穿透、路径逃逸、日志泄密、不可信预览
```

测试必须使用隔离沙箱，绝不能指向真实 NAS 资产。

## 22.11 CI 合并门禁

每个 PR、Codex worktree 或合并候选必须通过：

- 格式化、lint、静态分析与类型检查；
- 依赖与循环检测、架构边界测试；
- 公共契约兼容与生成 SDK 一致性检查；
- 数据库迁移前进/回滚或恢复测试；
- 单元、集成、契约、故障恢复和安全测试；
- 重复代码、复杂度与依赖体积阈值；
- 性能回归和敏感日志扫描；
- 许可证与依赖漏洞扫描。

M0-009 完成前不得进入 V0.1 的大规模产品实现。后续任何“暂时绕过”质量门禁都必须有已批准、带到期时间的技术债记录。

## 22.12 Codex 子任务要求

每个子任务必须明确回答：

1. 修改属于哪个模块，模块拥有者是谁；
2. 依赖方向是否符合本章；
3. 复用了哪些既有用例、契约或组件；
4. 是否复制了已有业务逻辑；
5. 是否新增语言、框架、运行时或重大依赖；
6. 是否新增/变更公开契约或数据库迁移；
7. 需要哪些架构、契约、故障与性能测试；
8. 产生了哪些技术债、风险和后续清理任务。

主协调线程必须检查 commit、diff、测试报告和 `architecture_review` 交接字段。功能可运行但破坏架构边界的实现必须拒绝合并。

## 22.13 不可接受的实现

以下任一情况均为合并阻断：

- 客户端或 Provider 直接访问 PostgreSQL；
- UI、Controller、WebDAV 或 MCP 自行实现权限和文件状态机；
- 跨模块直接写其他模块的数据表；
- Domain 引用 Infrastructure 或平台 API；
- Shell 进程加载网络、数据库、媒体解码或第三方重型代码；
- 新增语言/框架但没有 ADR；
- 静默吞错、无取消的无限等待、无幂等的可重试写请求；
- 复制粘贴核心业务逻辑；
- 引入万能 `Utils`、God Service 或循环依赖；
- 破坏无 AI/无可选 Provider 时的基础可用性；
- 无测试证明就声称完成文件安全、权限或性能要求。
