## 1. 目标与交付物

按卡交付**AssetLibrary 自己的一个网页**：选已登记库 → 后台有界精确查重 → 分页查看重复组与未验证项
→ 重新核对 → 导出绑定版本的 JSON 计划。全程只读：没有移动/复制/删除，没有执行入口，没有自动清理，
没有近似图比较、没有 AI 分类、没有「唯一文件」列表。

前端：`/dedup` 页面与侧栏「精确查重」入口，复用 `ReadOnlyWorkspace`、`WorkspaceNavigation`、
`workspaceRoutes`、`WorkspacePrimitives`、`WorkspaceIcon`、`SessionGate` 的既有语言。

后端：`AssetIdentity` 模块内的授权操作面 + 有界报告注册表，Host/Trial 组合根装配；六个操作走
`POST /assetlink/v1/dedup/{start|status|results|cancel|revalidate|export}`。

## 7. 风险与技术债

1. **报告保留是进程内的**：`DedupReportRegistry` 有界保留 8 份报告（每份 ≤20000 项），服务重启后报告
   不再可读。这是本卡明确的设计取舍：不新增迁移、不新增持久表，边界以契约里的 `RetentionBoundary`
   如实告知前端与用户，页面在报告缺失时显示「本次结果已不可读取」而不是空结果。若后续要求跨重启可读，
   需要一次新的迁移（编号从 `0024_asset_identity_*` 起）与协调裁决。
2. **体积预算**：见 4.4 第 2 项。门禁求和口径下车削无可再削的结论与实测四值都在那里；恢复 327680 需要
   协调裁决（分项预算或删视图），本卡不自行豁免、也不改门禁口径。
3. **真实端到端证据缺失**：见第 5 节最后一行；`run_e2e.py` 目前也没有查重操作步骤，加入后需在具备
   PostgreSQL 的环境执行。同一原因下，「已登录管理员在环回地址上走通六个操作」也未被任何门禁执行：
   认证中间件依赖数据库账号存储（`GatewayAuthenticationRuntime`），本机不可用；未登录边界与答案形状
   分别由新增的端点路由用例与线格式用例覆盖。
4. **`IDedupJobSignal` 是进程内唤醒信号**：不承载业务事实，作业事实仍只在持久任务中；丢弃信号只损失
   一个轮询周期。属「不新增调度器」约束下的最小实现，已记录在职责与依赖表第 4 节。
5. **五处 `CA1506` 抑制**（`DedupJobService`、`DedupJobWorker`、`DedupFindingClassifier`、
   `TrialDedupComposition`、`TrialDedupOperations`）：均为「单个工作台的门面 / 两种载荷并集的工作器 /
   组合根 / 已授权 HTTP 面」的类型计数，逐条带 `Justification`；规则本身仍拆在独立组件中。
   `DedupJobWorker` 的抑制带明确理由：它必须同时持有分析与复核两条载荷形状，拆开会让「同一租约下两种
   作业」的围栏逻辑分散到两处。
6. **未改契约**：`changed_contracts` 为空——新增的 `AssetIdentity/Contracts/DedupJobContracts.cs` 是本
   模块自己的新契约文件，未修改任何已发布/共享契约（AssetLink 契约、权限模型、统一错误码、根依赖锁）。
