## 1. 目标与交付物

按卡交付**AssetLibrary 自己的一个网页**：选已登记库 → 后台有界精确查重 → 分页查看重复组与未验证项
→ 重新核对 → 导出绑定版本的 JSON 计划。全程只读：没有移动/复制/删除，没有执行入口，没有自动清理，
没有近似图比较、没有 AI 分类、没有「唯一文件」列表。

前端：`/dedup` 页面与侧栏「精确查重」入口，复用 `ReadOnlyWorkspace`、`WorkspaceNavigation`、
`workspaceRoutes`、`WorkspacePrimitives`、`WorkspaceIcon`、`SessionGate` 的既有语言。

后端：`AssetIdentity` 模块内的授权操作面 + 有界报告注册表，Host/Trial 组合根装配；六个操作走
`POST /assetlink/v1/dedup/{start|status|results|cancel|revalidate|export}`。

只用六个已授权操作，没有任何路由桩：

| 步骤       | 驱动方式                                        | 断言                                                                                     |
| ---------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 未登录拒绝 | 无 Cookie 直接 POST 六个操作                    | 每个都 401 `authentication_required`，且答案里不含它命名的库/任务                        |
| `start`    | `POST /dedup/start`（库 + 操作键）              | 受理即 `queued`/`leased`、`report_available=false`、版本名为空                           |
| `status`   | 轮询 `POST /dedup/status`                       | 等到 `report_available=true`，版本等于 `{task_id}:1`，重复组数 > 0，计划状态非空          |
| `results`  | `POST /dedup/results`                           | 页自带 `analysis_version`，`total>0`，重复组**两个成员**都在                             |
| `revalidate` | `POST /dedup/revalidate`（先回执后轮询）      | 回执 `pending`，随后 `completed`、`plan_still_current=true`                              |
| `export`   | `POST /dedup/export`（带版本 + 摘要）           | 版本一致、`grants_file_operation=false`、组数 > 0；换一个版本号导出 → 409 `dedup_version_conflict` |
| `cancel`   | `start` 后 `POST /dedup/cancel`                 | 取消被记到持久任务上，任务落终态，且**取消不产生任何报告**                               |
| 重启后     | `host.RestartAsync()` 后读同一 `task_id`        | 同一 `task_id` 仍可读（租约/任务在 TaskHealth），`report_available=false`；`results` 返回 `dedup_report_not_retained`、`groups` 为空、`total=0`；再 `revalidate` → 404 `dedup_report_not_retained` |
| 只读       | 结束时逐个文件比对 SHA-256 与 mtime             | 合成源**一个字节都没变**                                                                 |
| 真实租约   | `DedupTrialLeaseProbe`：同一 `TrialDedupServices.Coordinator`（真实 `task_health` 函数） | 入队 → 认领（`leased`、`attempt=1`、租约窗口未过期）→ **心跳续租 `Accepted`** 且任务 `updated_at` 前进 → 在租约下 `finish` 为 `succeeded` → 用已终结的 identity 再续租被拒 `NotCurrent` |

心跳为什么要单独驱动：worker 只在一次尝试**超过一个心跳间隔（2 秒）**时才续租，而合成源 48 MiB 的哈希
快于该间隔，从 HTTP 面观察「续租」只能是时序巧合。所以心跳不走轮询，而是用**同一个协调器、同一套真实
`task_health` SQL**按名字驱动一次完整租约生命周期（入队/认领/续租/在租约下完成/失去租约后被拒），
断言全部落在存储的回答上。`status` 轮询同时断言「活动期间状态不变而 `updated_at` 前进」，作为工作器
确实持有租约的旁证。

「迟到复核不得覆盖新报告」这一条**在试运行里无法确定性触发**：worker 单线程、按认领顺序串行执行，
一个复核的扫描与落盘之间不会插进另一次分析。因此该竞争用**进程内确定性用例**
`DedupRecheckFenceTests.ALateVerdictNeverReplacesANewerAnalysisOfTheSameLibrary` 覆盖（合成双文件库 +
真实 `DedupJobWorker` + 带围栏探针，在扫描中途发布更新的一次分析、**旧 key 仍保留**），并已用反向探针
确认有效：把 `File` 换回上一轮的非原子写法后该用例立即失败
（`Assert.AreNotEqual 失败。应为: <6499ee26-…> 以外的任意值，实际为: <6499ee26-…>`，即旧复核确实把
`latest` 抢了回去），换回修复后 4 项全绿。两类证据互补，均在交接材料中列出。
