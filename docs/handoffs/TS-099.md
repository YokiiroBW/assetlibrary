## 1. 本卡做了什么

在 `OperationTrash` 模块内实现**资产成品包只读预检**：给定 staging 根、`staging_ref`、清单字节与
调用方声明的原始字节摘要，在**零写入**前提下判断成品包是否完整可信，并给出发布目标目录名。

四个强制层各司其职，依赖方向严格为 `Infrastructure -> Application -> Domain`：

- `Contracts`：请求/报告/问题/去重汇聚器；冻结 22 个错误码与 7 条 `unverified`。
- `Domain`：清单语义（身份、布局、文件集、预算上限）与原始路径词法策略；**不含 `System.IO`**。
- `Application`：端口（授权 scope、卷空间、时钟、哈希）、全部预算常量、编排服务。
- `Infrastructure`：`System.Text.Json` 严格读取、真实文件系统预检、根锚定与枚举、流式哈希。

## 3. 必须知道的三个纠正

1. **越界文件已删除。** `Infrastructure/StrictJsonReader.cs` 不在白名单，已删除且从未进入 git；
   JSON 一律使用 .NET 自带 `System.Text.Json`，严格性由 `JsonDocumentOptions` 加上重复键、
   原始整数词法、UTF-8 与字节预算检查实现。仓库内没有第二套通用 JSON 解析器。
2. **两种摘要不可混用。** 请求 `expected_digest` 是收到字节的**原始** SHA-256，不做 LF 归一化、
   不重新序列化；夹具/清单锁定摘要用 **LF 归一化**字节。候选 `manifest.json` 的 LF 摘要为
   `b523ba439ded3950e1ac3dcc483dcba3e3f90b4848f2e662377e770f3637db5f`。
   早期把 Windows CRLF 分发字节摘要当成清单摘要是错的，已纠正并有测试固化。
3. **复制来的包缓存不是可信性证明。** 本卡对 50 个在解内锁定包做了双向独立核对：
   `packages.lock.json` 的 `contentHash` 与缓存 `.nupkg.metadata` 一致 50/50；
   `.nupkg` 字节 SHA-512 与 `.nupkg.sha512` 一致 50/50。`dotnet restore --locked-mode` 实际通过。
